## 二、当前 RAG 实现方式总结

### 1. 总体架构（五环节流水线）

独立问答页 `http://localhost:4175/rag`（免登录），路由 `/api/rag/*`（后端 `backend/rag.py`，不嵌套 3D 首页）。

```
用户提问
  → ① 意图路由（按优先级 if-else 正则：作息 → 宿舍 → 周课量 → 规模统计 → 课表[可带路径] → 培养方案 → 兜底）
  → ② 槽位抽取（正则/词典：班级名、学生名、周几、第N大节、上午/下午/晚上、冬季/夏季、起点）
  → ③ 确定性工具函数（tool_schedule / tool_timetable / tool_student / tool_dorm / tool_route）
  → ④ 时间与季节解析（按当前日期自动选夏/冬作息、周末回退下一上课日）
  → ⑤ 回答合成（模板 + sources[] 数据溯源）
```

**关键设计**：检索与推理全部走确定性代码（零幻觉、可溯源），只有"理解层"用模式匹配。若将来接入 LLM，仅替换 ①/②，③④⑤ 不动。

### 2. 数据体系（`data/rag/*.json`，由 `scripts/generate_rag_data.py` 生成，seed 固定可重跑）

- **6 个班级** 计科1班~计科6班 × 60 人 = **360 名学生**（2025 年秋季入学，当前大二上 2026-2027-1；无重名）
- **60 间宿舍**：每间 6 人、分性别住宿；计科N班 → 公寓 B1N（每班 10 间），宿舍房间码与 3D 模型 `room_anchors.json` 一一对应
- **培养方案**：8 门必修全班一致 + 每班 2 门不同选修（各 2 学分），共 25 学分；每 3 班 1 名辅导员
- **大二上排课 96 条**：生成器内置校验「班级×大节 / 教师×大节 / 教室×大节」三重唯一 + 宿舍容量/分性别/房间已建模（`validation.json` 全 PASS）
- **双季作息**：10.1 前夏季（下午 14:30 上课），国庆后冬季（14:00 上课）

### 3. 检索工具（function calling 形态，`/api/rag/tools`）

`timetable_for`（按日期取作息）/ `tool_schedule` / `tool_student` / `tool_dorm` / `tool_location_of`（房间码→3D 语义位置）/ `tool_route`（室外 Dijkstra + 室内锚点段，多目的地按大节时间排序）。

### 4. 时间与季节解析（时间类问题准确的关键）

- 解析：今天/明天/后天/周X/上午/下午/晚上/第N大节；非上课日自动回退下一上课日
- 季节：问题含"冬季/夏季"时**覆盖**当前日期强制执行对应作息；否则按当前日期（10.1 分界）自动切换
- 精确到班：如「冬季作息的周四几点下课」→ 查该班周四最后一节课并给出下课时刻与双源溯源

### 5. 溯源与评测

- 每条回答携带 `sources[]`（timetable.json / schedule.json / students.json / road_graph.json），页面点击溯源徽标即在左侧源数据浏览器高亮对应记录
- `/api/rag/eval` 内置评测集现 **12 条，12/12 通过**，覆盖：作息季节、课表、周课量、宿舍、路径、规模统计、聚合统计、培养方案

### 6. 已知边界（为什么部分"简单问题"会漏答）

规则管道的表达能力 = 手工枚举的句法模板数。两类典型缺陷：

1. **单实体抽取**：早期 `detect_class()` 只取第一个匹配班级 → 「计科1班、计科2班、计科3班加起来总共多少人」只答计科1班 60 人
2. **无聚合/比较算子**：没有"加起来/分别/比…多/最多"等运算语义的解析路径，未枚举的问法落入兜底

## 三、泛化简单问题的实现方案

### A. 已落地（v2）：实体枚举 + 聚合算子

理解层从"单模板"升级为"**实体收集 + 算子判定**"：

- **实体**：`detect_all_classes()` 全局正则一次性收集句中全部「计科X班」（支持 、/，/和/与/加 连接、中文数字），不再取第一个
- **求和算子**：「加起来 / 加在一起 / 一共 / 总共 / 合计」→ 逐班统计后求和（含宿舍合计与逐班明细）
- **分组算子**：「分别 / 各」→ 逐班分组展示

已验证问法（均已入评测集）：

| 问法 | 回答 |
|------|------|
| 计科1班、计科2班、计科3班加起来总共多少人？ | 180 名（逐班 60），住宿 30 间 |
| 计科4班与计科5班分别多少人？ | 逐班 60 人（各 10 间宿舍） |
| 计科一班和计科二班总共多少人？ | 120 名（中文数字"一/二"已识别） |
| 计科1班周一到周五都有几节课？ | 周一4/周二3/周三3/周四4/周五2，共 16 节 |

### B. 中长期：可解释 QueryPlan + 两条翻译路径（共用一套执行器）

把"理解层"产出统一为结构化查询计划，执行层（工具函数 + 溯源）保持不变：

```jsonc
// 目标 QueryPlan 示例（单班/多班/全部、求和/分组/比较/极值 通用）
{
  "intent": "stats",
  "aggregate": "sum",                 // sum | group | compare | max | min
  "entity": { "type": "class", "items": ["计科1班", "计科2班", "计科3班"] },
  "metric": "students",               // students | courses_per_week | dorm_rooms | credits
  "window": "week"                    // 时间窗口（周课量类）
}
```

两条翻译路径：

1. **LLM function calling（推荐接入后替换 ①/②）**：让大模型输出上述 JSON Schema 约束的计划 → 现有工具执行。答案准确率仍由代码兜底，LLM 只负责"理解"。`/api/rag/tools` 已按 function calling schema 声明工具清单，可直接对接。
2. **本地语义引擎（无 Key 方案）**：维护计量单位词表（人/间/节/门/学分）+ 聚合/比较词典，把"简单算术问答"（求和、比较、极值、全部实体通配）做成独立子引擎，覆盖"所有班/几个班加起来/哪班最多/比…多几个"等问法。

### C. 落地步骤建议

1. 定义 `QueryPlan` JSON Schema 与 `execute_plan(plan) → {answer, sources, data}` 执行器（把现有分支重构为 plan 的分发）
2. 接入 LLM function calling 生成 plan；无 Key 时回退本地翻译器，两者共用执行器 → 结构上消除"模板穷举"
3. 评测集持续扩充（每个新算子补 ≥2 条用例），`/api/rag/eval` 作为回归闸门
4. 跨域泛化（跨字段比较，如"某班人数是否比课多的班多"）放后续：先保证同一字段内的聚合/比较/极值完备
