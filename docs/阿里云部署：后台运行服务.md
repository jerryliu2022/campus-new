# 阿里云 ECS 上后台运行前后端服务

> 适用：阿里云 ECS（Linux，CentOS 7/8、Alibaba Cloud Linux、Ubuntu 均可）
> 默认代码放在 `/opt/campus-new`，下文所有命令都以此为准，换成你的实际路径即可。

---

## 0. 先想清楚：服务器上其实可以只跑一个进程

本地开发必须开两个终端（vite 热更新），但**部署到服务器不需要**。三种形态，按推荐度排序：

| 形态 | 跑什么 | 访问端口 | 适用场景 |
|---|---|---|---|
| **① 单进程（推荐入门）** | 只跑 uvicorn `:8000` | `http://公网IP:8000/` | 最省事。项目 `backend/main.py` 检测到 `dist/` 存在会**自动托管前端 SPA**，三个页面都在 8000 上 |
| **② Nginx 反向代理（推荐正式）** | uvicorn `:8000` + nginx `:80` | `http://公网IP/` | 不用暴露端口号，可做域名和 HTTPS |
| **③ 同本地（vite dev）** | uvicorn `:8000` + vite `:4175` | `http://公网IP:4175/` | 只在服务器上边改边调时临时用；vite dev 吃内存、无压缩、源码暴露，**不要长期跑** |

形态 ① 和 ② 都需要先 `npm run build` 打包一次（`dist/`）——**没打包的话形态 ① 会只剩接口、没有页面**。

## 1. 前置准备（只需做一次）

### 1.1 阿里云安全组放行端口（最容易忘的一步）

ECS 控制台 → **实例 → 安全组 → 配置规则 → 入方向 → 手动添加**：

| 端口 | 授权对象 | 用途 |
|---|---|---|
| `8000` | `0.0.0.0/0` | 形态 ① 直接访问；调试接口用 |
| `80` | `0.0.0.0/0` | 形态 ② Nginx |
| `4175` | `0.0.0.0/0` | 仅形态 ③ 需要 |
| `22` | 你的 IP | SSH |

> 安全组没放行的话，服务在服务器上跑得好好的，你本地就是连不上，且**没有任何报错**。

如果系统内还开了防火墙，也要放行（二选一，看你的系统）：

```bash
# firewalld（CentOS / Alibaba Cloud Linux）
sudo firewall-cmd --permanent --add-port=8000/tcp && sudo firewall-cmd --reload

# ufw（Ubuntu）
sudo ufw allow 8000/tcp
```

### 1.2 装环境

```bash
# Node —— vite 6 要求 Node ^18 || ^20 || >=22，装 20 最稳
curl -fsSL https://rpm.nodesource.com/setup_20.x | sudo bash -   # CentOS
sudo yum install -y nodejs
# Ubuntu: curl -fsSL https://deb.nodesource.com/setup_20.x | sudo bash - && apt install -y nodejs

node -v   # 确认 >= 18

# Python —— 项目代码 3.8+ 即可（所有 3.9+ 语法都有 from __future__ import annotations 兜底）
python3 -V
```

### 1.3 装依赖

```bash
cd /opt/campus-new
sudo python3 -m pip install --upgrade pip
sudo python3 -m pip install -r requirements.txt     # 后端，就 3 个包
npm install                                          # 前端，package.json 里有清单
```

`requirements.txt` 只锁了 `fastapi` / `uvicorn` / `pydantic` 三个包（其余传递依赖由 pip 自动解析），
版本与本机实测环境一致。想在服务器上固定到完全一致的环境，也可以：

```bash
sudo python3 -m pip install "fastapi==0.124.4" "uvicorn==0.33.0" "pydantic==2.10.6"
```

### 1.4 CRLF 换行坑（本项目一定会踩）

项目文件是 Windows **CRLF** 换行，拷到 Linux 上跑 `.sh` 脚本会报：
`/bin/bash^M: bad interpreter: No such file or directory`

```bash
# 装转换工具
sudo yum install -y dos2unix        # Ubuntu: apt install -y dos2unix

# 只转换脚本文件即可（不要对整个项目跑，会污染 git diff）
dos2unix scripts/deploy/*.sh
```

没有 dos2unix 就用 sed：

```bash
sed -i 's/\r$//' scripts/deploy/*.sh
```

### 1.5 打包前端（形态 ① ② 必做）

```bash
cd /opt/campus-new
npm run build      # 产出 dist/
```

> 服务器上 `npm run build` 需要内存，**1G 内存的机器可能构建失败**，建议 2G 以上，或者在你本机 build 完把 `dist/` 传上去。

## 2. 后台运行的三种姿势

### 姿势 A：`setsid` + `nohup` + `&`（最快，不持久）

```bash
cd /opt/campus-new
mkdir -p logs

# 后端
setsid nohup python3 -m uvicorn backend.main:app --host 0.0.0.0 --port 8000 \
  </dev/null >> logs/backend.log 2>&1 &
echo $! > logs/backend.pid

# 前端（仅形态 ③ 需要）
setsid nohup npx vite --host 0.0.0.0 --port 4175 \
  </dev/null >> logs/frontend.log 2>&1 &
echo $! > logs/frontend.pid
```

四个零件缺一不可：

| 零件 | 作用 | 少了会怎样 |
|---|---|---|
| `&` | 放到后台 | 命令占着前台，Ctrl+C 或断连就没 |
| `nohup` | **忽略 SIGHUP**（SSH 断开时内核发给会话的首信号） | 断连即死，最常见的挂法 |
| `setsid` | 让进程**自立为新会话组长**，彻底脱离当前终端会话 | 撞上 systemd-logind 的用户进程清理时会被连带杀掉（见第 8 节） |
| `</dev/null` | 切断 stdin | 进程一旦想读终端，会收到 SIGTTIN 被**挂起**（状态变 `T`，看着像"卡死"） |

另外两个注意点：

- 用 `>>` 追加而不是 `>`，免得重启一次日志就被清空，连死因都查不到。
- **服务器重启后进程不会自动回来**，长期跑请直接用姿势 C（systemd）。

> 如果你"明明写了 nohup 还是挂"，别着急改命令，先看第 8 节的排查清单——
> 大概率是管道、`sudo` 位置或 systemd-logind 在作怪，换命令也治不好。

查看 / 停止：

```bash
tail -f logs/backend.log          # 实时看日志
kill $(cat logs/backend.pid)      # 停止
ps -ef | grep uvicorn             # 确认还活着
```

---

### 姿势 B：`screen` / `tmux`（随时回来看输出，适合调试）

```bash
sudo yum install -y screen        # Ubuntu: apt install -y screen

screen -S backend                 # 进入一个叫 backend 的会话
python3 -m uvicorn backend.main:app --host 0.0.0.0 --port 8000
# 按 Ctrl+A 然后按 D  →  脱离会话（进程继续跑）

screen -S frontend
npx vite --host 0.0.0.0 --port 4175
# Ctrl+A D

screen -ls                        # 查看有哪些会话
screen -r backend                 # 回到 backend 会话看输出
# 在会话里 Ctrl+C 再 exit 就结束
```

断线重连后 `screen -r backend` 画面原样恢复，调试时比看日志文件舒服。

---

### 姿势 C：`systemd`（推荐，开机自启 + 崩溃自动拉起）

两个 unit 文件，我放在 `scripts/systemd/` 下，改好路径后拷过去：

```bash
cd /opt/campus-new

# 先按你的实际环境改两处：WorkingDirectory 和 ExecStart 里的 python/npx 绝对路径
which python3 npx        # 查绝对路径

sudo cp scripts/systemd/campus-backend.service /etc/systemd/system/
sudo cp scripts/systemd/campus-frontend.service /etc/systemd/system/   # 形态 ③ 才需要

sudo systemctl daemon-reload
sudo systemctl enable --now campus-backend      # enable=开机自启，now=现在就启动
sudo systemctl enable --now campus-frontend
```

常用命令：

```bash
systemctl status campus-backend      # 看状态、最近几行日志
systemctl restart campus-backend     # 重启
systemctl stop    campus-backend
journalctl -u campus-backend -f      # 实时日志（Ctrl+C 退出）
journalctl -u campus-backend --since "10 min ago"
```

`Restart=always` 已经在 unit 里配好，**进程崩了 3 秒后自动重启**；服务器重启也会自动拉起来。这是长期运行唯一靠谱的方案。

## 3. 一键脚本（不想记命令就用这个）

我写好了 `scripts/deploy/ctl.sh`，把上面那些封成四个子命令：

```bash
cd /opt/campus-new
dos2unix scripts/deploy/ctl.sh        # 必须先转格式，否则 ^M 报错

./scripts/deploy/ctl.sh start         # 后台启动（后端 + 前端）
./scripts/deploy/ctl.sh start-backend # 只启后端（形态 ① ② 用这个）
./scripts/deploy/ctl.sh status        # 看端口、PID、进程是否活着
./scripts/deploy/ctl.sh log backend   # 看后端日志（tail -f）
./scripts/deploy/ctl.sh restart
./scripts/deploy/ctl.sh stop          # 全部停止
```

脚本用 `setsid nohup` 启动，SSH 断开不受影响；PID 记在 `logs/*.pid`，日志在 `logs/*.log`。

## 5. 关于跨域（CORS）——本项目基本不用管

`backend/main.py` 里的 CORS 白名单只放行了 `localhost:4175` / `127.0.0.1:4175`，看着像会拦外网访问，其实**不会**，因为：

- 形态 ①：页面和接口都在 `8000`，**同源**；
- 形态 ③：浏览器访问 `IP:4175`，`/api/**` 由 **Vite 服务端转发**到 8000，浏览器只看到 4175，也是同源；
- 形态 ②：Nginx 反向代理同理。

只有当你的前端和后端**部署在不同域名**时（比如前端挂在 CDN、后端单独一个域名），才需要改：

```python
# backend/main.py 第 25 行附近
app.add_middleware(CORSMiddleware,
    allow_origins=["http://47.xx.xx.xx:4175", "https://your.domain.com"],
    allow_methods=["*"], allow_headers=["*"])
```

## 6. 常见问题

| 现象 | 排查 |
|---|---|
| 外网打不开，服务器本地 curl 正常 | 阿里云**安全组**入方向没放行端口（见 1.1） |
| 写了 `nohup`，SSH 一断进程还是没了 | nohup 只挡 SIGHUP 一种死法，还有 5 种 → 见 **第 7 节** |
| `/bin/bash^M: bad interpreter` | CRLF 换行，`dos2unix scripts/deploy/*.sh` |
| 后端启动报 `ModuleNotFoundError: fastapi` | 没装依赖，或用了另一个 python。`sudo python3 -m pip install -r requirements.txt` |
| `address already in use` | 端口被占：`lsof -i :8000` 或 `ss -lntp \| grep 8000`，然后 kill 掉 |
| vite 报 Node 版本警告 / 起不来 | Node < 18。vite 6 要求 `^18 \|\| ^20 \|\| >=22` |
| 进程过一会儿就没了 | 多半是内存不足被 OOM kill。`dmesg \| grep -i oom`。1G 机器别同时跑 vite dev + 3D 场景 |
| 形态 ① 只有接口没有页面 | 忘了 `npm run build`，`dist/` 不存在，后端不挂载 SPA |
| 后端改了代码没生效 | uvicorn 没开 `--reload`，需要重启（systemd 用 `systemctl restart`） |
| 想跑多进程提高并发 | `uvicorn ... --workers 4`（注意：本项目 `init_db()` 会写库，多 worker 建议先跑通单进程再说） |

## 7. SSH 一断开服务就挂 —— 排查清单

`nohup` 只挡得住 SIGHUP 一种死法。下面按概率列出六种，对号入座即可。

### 先确认是真的"挂了"，不是连不上

```bash
ps -ef | grep -E "uvicorn|vite" | grep -v grep
ss -lntp | grep -E ":8000|:4175"
```

进程还在、只是外网连不上 → 根本不是这个问题，回去看 **1.1 安全组**。

---

### 根因 ①　只写了 `&`，漏了 `nohup`（最常见）

SSH 断开时内核会给该会话的所有进程发 **SIGHUP**，默认动作就是终止。

```bash
python3 -m uvicorn ... &        # ❌ 断连即死
nohup python3 -m uvicorn ... &  # ✅
```

---

### 根因 ②　命令里混了管道（`| tee`）

```bash
nohup python3 -m uvicorn ... | tee -a logs/backend.log &   # ❌
```

bash 会为管道**两段各起一个进程**，`nohup` 只护住了左边那个。`tee` 没保护，断连时被 SIGHUP 杀掉；
之后 uvicorn 继续往已关闭的管道写 → 收到 **SIGPIPE** → 照样死。
所以你明明写了 nohup，还是挂。

> 改用重定向，别用 `tee`；想边跑边看就另开一个 `tail -f logs/backend.log`。

---

### 根因 ③　`sudo` 和 `nohup` 的位置反了

```bash
nohup sudo python3 -m uvicorn ... &    # ❌
sudo nohup python3 -m uvicorn ... &    # ✅
```

sudo 出于安全考虑会**把信号处理恢复成默认**，于是 nohup 设的"忽略 SIGHUP"被抹掉了。

---

### 根因 ④　nohup 没作用到真正的进程上

```bash
nohup cmd1 && cmd2 &          # ❌ nohup 只包住 cmd1
nohup (cd /opt && python3 ...) &   # 多一层子 shell，行为依赖具体 shell
```

用 `setsid` 兜底最省心，它让整棵进程树自立门户。

---

### 根因 ⑤　systemd-logind 在清理用户进程（Ubuntu / 新版系统常见）

当 `/etc/systemd/logind.conf` 里是 `KillUserProcesses=yes` 时，**你最后一个 SSH 会话结束后，
systemd 会把这个用户名下的残留进程一并清掉**。这是 cgroup 级别的清理，**nohup 完全拦不住**，
所以无论你怎么改命令都没用——这也是"nohup 明明写了还是死"的第二个大坑。

```bash
# 查看当前设置
grep -i KillUserProcesses /etc/systemd/logind.conf

# 解决（推荐第一种，不用重启服务）
sudo loginctl enable-linger $USER

# 或者全局关掉
sudo sed -i 's/^#\?KillUserProcesses=.*/KillUserProcesses=no/' /etc/systemd/logind.conf
sudo systemctl restart systemd-logind
```

---

### 根因 ⑥　其实不是断连杀死，是 OOM

1G 内存的机器上跑 vite dev + 3D 场景，进程很可能在**你断开之前**就被内核 OOM kill 了，
只是时间上撞在一起，看起来像"一断就挂"。

```bash
sudo dmesg -T | grep -i "killed process" | tail -5
# CentOS / Alibaba Cloud Linux 也可以看：
sudo grep -i "out of memory" /var/log/messages | tail -5
```

---

### 一步验证：进程到底脱离终端了没

```bash
ps -o pid,ppid,pgid,sid,tty,stat,cmd -p $(cat logs/backend.pid)
```

对照这三项：

| 字段 | 正常应该是什么 | 不对说明什么 |
|---|---|---|
| `TTY` | `?` | 显示 `pts/0` 之类 = 还绑着终端，断连会挨 SIGHUP |
| `SID` | 等于自身 PID（setsid 的效果），且 ≠ 你 shell 的 SID | 和你 shell 同会话 = 会被连带清理 |
| `STAT` | `Ssl` 之类，**不含 `T`** | 有 `T` = 被 SIGTTIN 挂起了，补 `</dev/null` |

查自己 shell 的 SID：`ps -o sid= -p $$`

---

### 结论

- **临时验证**：`setsid nohup 命令 </dev/null >> logs/xxx.log 2>&1 &`
- **长期运行**：直接用 **姿势 C（systemd）**。systemd 管的进程跑在独立 cgroup 里，
  不挂在任何 SSH 会话下，上面 ①~⑤ 一个都不会发生，还自带开机自启和崩溃自动拉起。

## 8. 附：形态 ② 的 Nginx 配置参考

```nginx
server {
    listen 80;
    server_name 47.xx.xx.xx;      # 或你的域名

    root /opt/campus-new/dist;
    index index.html;

    # 前端 SPA：三个页面都靠这一段回退到 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 接口反代到后端
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # GLB 模型 6.4MB，开 gzip 会快很多
    gzip on;
    gzip_types application/javascript text/css application/json;
    client_max_body_size 20m;
}
```

改完 `sudo nginx -t && sudo systemctl reload nginx`。
